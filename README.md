# EPUB / TXT 繁簡轉換與章節拆分工具

純前端、單一 HTML 檔案的小說處理工具，不需要伺服器，所有運算都在瀏覽器端完成，
檔案不會被上傳到任何地方。

提供三個處理步驟，**可以分開單獨使用，也可以勾選多個同時執行**：
1. 簡繁字詞轉換
2. 修復 EPUB 圖片缺少 alt 屬性的錯誤
3. 小說章節自動拆分

若同時勾選「簡繁字詞轉換」與「章節拆分」，執行順序固定是「先完成簡繁轉換／字詞替換，
再用轉換後的文字進行章節拆分」，也就是說輸出的每個章節檔案內容都已經是轉換後的文字
（例如：上傳簡體 EPUB，先轉繁體、套用字詞替換規則，再依章節拆成一個個 txt 檔）。

## 功能一：簡繁字詞轉換

### 功能說明
- 支援 `.epub` 與 `.txt`，可處理單一/多個獨立檔案，也可處理整個資料夾（含多層子資料夾）
- OpenCC 轉換模式可選：簡體➔臺灣正體（含常用詞彙修正）、簡體➔臺灣正體（僅字體）、
  簡體➔傳統繁體、繁體➔簡體、或不使用 OpenCC
- 可自訂多組「找字詞→換字詞」規則，於 OpenCC 轉換之後套用，用來統一修正人名、專有名詞等
- 檔名與資料夾結構完全維持原樣，只有檔案內容被轉換

### 運作原理
EPUB 檔案本質上是一個 zip 壓縮檔。轉換流程：
1. 用 **JSZip** 解壓縮 `.epub`；`mimetype` 檔案原封不動保留
2. 對 `.html / .xhtml / .htm / .ncx / .opf / .xml / .txt / .css` 這幾類文字檔案進行處理：
   先把 `href`/`src` 屬性的網址做 `decodeURIComponent` 還原，避免轉換誤傷百分號編碼字元；
   用 **OpenCC-JS** 執行簡繁字元／詞彙轉換；再套用自訂字詞替換規則；
   最後自動把 `<?xml encoding=...?>`、`<meta charset=...>` 修正為 `utf-8`
3. 圖片、字型等非文字類檔案原封不動複製
4. 用 **JSZip** 重新打包回 `.epub`

`.txt` 則是直接讀取文字內容，依序套用 OpenCC 轉換與自訂字詞替換規則後輸出。

資料夾模式使用瀏覽器的檔案系統存取 API（`webkitGetAsEntry` / `webkitdirectory`）
遞迴掃描整個目錄樹，逐一轉換內容後用 JSZip 重新打包成一個 zip，結構與檔名完全不變。

## 功能二：修復 EPUB 圖片缺少 alt 屬性的錯誤

### 功能說明
修復這類 EPUB 驗證錯誤：

```
error on line 11 at column 108:
Specification mandates value for attribute alt
```

這是 XHTML 規範的要求：`<img>` 標籤必須要有 `alt` 屬性（用於螢幕閱讀器、圖片無法顯示時的替代文字），
缺少這個屬性會被判定為驗證錯誤。此功能會掃描 EPUB 內所有 `.html` / `.xhtml` / `.htm` 檔案，
找出沒有 `alt` 屬性的 `<img>` 標籤並補上 `alt=""`；已經有 `alt` 屬性的圖片則不會被更動。

這個修復只對「最終輸出仍是 EPUB」的情況有意義（也就是沒有同時勾選「章節拆分」時）。
若同時勾選了章節拆分，該檔案最終會被轉換成純文字的章節檔，不含任何 HTML 標籤，
此修復在這種情況下不會產生實際作用。

### 運作原理
用正則表達式逐一掃描 `<img ...>` 標籤：先檢查標籤內是否已經有 `alt=` 屬性，
若沒有，就在標籤結尾（自我封閉 `/>` 或一般 `>` 之前）補上 `alt=""`，並保留
原本標籤內其他所有屬性與自我封閉寫法不變。

## 功能三：小說章節自動拆分

### 功能說明
把一本小說（`.epub` 或 `.txt`）依章節標題自動拆分成多個獨立的 `.txt` 檔案，
每個章節一個檔案，並依序編號。支援單一/多個獨立檔案，也支援整個資料夾批次處理。

章節判斷規則會辨識以下格式作為新章節的起點：
- 「第X章／回／卷／節」（X 可為阿拉伯數字或中文數字）
- 「Chapter N」
- 序章、序幕、前言
- 終章、尾聲、結語、後記
- 番外篇、番外章
- （電子書／電子版／店鋪／店舖／限定／封入）特典篇

在第一個章節標題出現之前的內容，會被視為「前言與簡介」獨立存成一個檔案。
拆分後也會自動過濾掉純分隔線（如 `***`、`———`、`~~~` 等），並壓縮多餘的空行。

獨立檔案模式：每本小說拆分後打包成一個 zip 下載（zip 內就是各章節的 txt 檔）。
資料夾模式：維持原始目錄結構，每個小說檔案原地替換成一個同名的「＿章節拆分」子資料夾，
裡面放著拆出來的章節檔案，其餘非小說類檔案原樣保留，最後整個打包成一個 zip。

### 與簡繁轉換組合使用時
若同時勾選「簡繁字詞轉換」，處理順序是：先從 EPUB/TXT 擷取出完整文字內容，整段套用
OpenCC 轉換與自訂字詞替換規則，**再用轉換後的文字**去比對章節判斷規則進行拆分。
也就是說章節標題本身（例如簡體的「第一章」）也會先被轉換過，才拿去判斷／命名檔案，
輸出的每個章節 txt 內容自然也都已經是轉換後的文字。

### 運作原理
此功能移植自 `split_novel_by_chapter.command`（原本是本機端 Python 腳本），
核心規則（章節判斷正則、分隔線過濾正則、章節內容清理邏輯）與原腳本完全相同。

- **TXT**：讀取檔案位元組後嘗試以 `utf-8` → `gbk` → `big5` → `utf-16le` 依序解碼，
  取第一個能成功解碼的編碼
- **EPUB**：
  1. 解析 `META-INF/container.xml` 找出 `.opf` 檔案路徑（找不到就退而求其次搜尋
     壓縮包內任何 `.opf` 檔）
  2. 解析 `.opf` 的 manifest（`<item id=... href=...>`）與 spine（`<itemref idref=...>`）
     取得書籍實際的閱讀順序
  3. 依序讀出每個章節檔案，剝除 HTML 標籤只留文字內容（`<style>`/`<script>`/`<head>`
     整段忽略，`<p>/<br>/<div>/<h1~h6>/<tr>` 前後轉換為換行，藉此還原基本排版）
  4. 把所有章節文字依序串接起來，交給跟 TXT 共用的章節拆分邏輯處理
- **與原腳本的差異**：原腳本解析 manifest 時，`id` 與 `href` 是用兩個各自獨立的
  正則表達式分開擷取，若 `<item>` 標籤內兩個屬性的先後順序跟原腳本預期的不同，
  會導致解析失敗、無法正確取得章節內容。這裡改成針對「單一 `<item>` 標籤」同時
  擷取 `id` 與 `href`，不受屬性先後順序影響，修正了這個問題。
- 瀏覽器沒有本機檔案系統寫入權限，因此原腳本「固定輸出到 Downloads 資料夾、
  自動加時間戳記資料夾防止覆蓋」的行為，改為透過瀏覽器下載功能以 zip 檔案的
  形式一次性交付。
